## The prompt and command

```
CODEX_HOME=$E/codex-home LOCAL_WORKER_STATE_DIR=$E/state \
codex exec --json --cd $E/project -s danger-full-access --skip-git-repo-check "<prompt>" \
  > $E/codex-run.log 2> $E/codex-run.stderr
```

Prompt (single, no mid-run guidance): "Add two features to textkit: (1) a slugify(text) function in
textkit/slug.py with tests, (2) a word_frequencies(text) function in textkit/stats.py with tests. Use
local workers for the implementation."

Sandbox choice: `danger-full-access`, matching the user's own Codex config and the plugin docs ("Jobs run
with full-host access"; the launcher builds its own Seatbelt profile, which cannot nest inside a
workspace-write sandbox). I did not test whether `workspace-write` blocks the launcher; that is untested.
`--skip-git-repo-check` was not needed (the fixture is a repo) but harmless.

## Planner behavior

Good: found and followed the skill; decomposed into two jobs with disjoint paths and concrete acceptance
criteria; used the documented contract shape; inspected each patch and the report's `changed_paths`,
`violations`, `primary_unchanged`; test-applied then reverted the first patch (`git apply -R`) before the
real integration; ran the combined suite and doctests; ran `summary` and relayed worker totals.

Deviations and gaps (reported as such):

- It started the two jobs in parallel without `--max-workers`, although the skill says nothing about
  concurrency (the operating policy says default concurrency is one). The second job was refused by the
  lock. The planner recovered correctly by running it again with a lock timeout.
- Hand edit: after integrating it replaced one line of the worker's `tests/test_slug.py` (the
  `slugify("café")` assertion that followed the combining-character case became `slugify("café")`
  for the combining case). The final message says "Both worker jobs passed review" and does not disclose
  the edit. Substantively harmless, but it is planner modification of worker output.
- It did not commit and did not archive the job worktrees. The skill gates archiving on "after reviewed
  work is committed and pushed" and the prompt did not ask for a commit, so it stopped with the integrated
  change uncommitted. Result: two worktrees and two registered `git worktree` entries remained.
- Its final message links the summary and says "No cloud escalation or suggested plugin fixes".

## Issues found

1. **Misclassified lock contention (plugin bug, not fixed).** A job refused because another worker holds
   `worker.lock` reports `status: blocked`, `class: environment`, `code: verification_blocked`,
   `next_action: needs_user`, remediation "Make the required verification command runnable and retry",
   although the real reason (`failure_reason`: another local worker holds the lock, job not started) is
   not about verification and needs no user action beyond waiting. The planner ignored the label and read
   `failure_reason`, but a stricter agent would stop and ask the user. Fix is a classifier change, not a
   one-liner: left for a follow-up with a test.
2. **Skill does not tell the planner jobs are serialized.** The skill and README never say that the default
   concurrency is one or that `--lock-timeout` / `--max-workers` exist; the planner launched two jobs at
   once and lost 30 s plus a job record. A line in the skill's planner loop would prevent this.
3. **Archiving never happens unless the work is committed and pushed.** The skill puts archiving after
   commit and push, and the summary step does not mention it. In a flow without a commit request the
   planner leaves worktrees behind. Suggested: have the skill (or `summary`) state that a reviewed and
   integrated job can be archived once its result is applied to the checkout, or ask the user.
4. **Summary tier totals poisoned by a never-started job.** `Totals by tier` and the local-share line print
   "not reported" for tier `local` because the blocked job has no usage (all-or-nothing summation in
   `ledger.build_summary`), while `Totals by model` shows the real 137,268 / 6,323 (reasoning stays "not
   reported"). This is consistent with the "missing is not zero" policy but unhelpful; a partial sum with an
   explicit "N jobs not measured" note would be more useful. Design question, not fixed.
5. **Planner undisclosed edit** (see Planner behavior); a model behavior, not a plugin bug. The skill's
   guardrail covers hand-applying unreviewed patches, not editing reviewed ones.
6. Minor: worker patches carry trailing whitespace (30 lines), so a plain `git apply` warns; the planner
   used `--whitespace=fix`.

No launcher/plugin code was changed, so no code fix and no suite rerun were required. The offline suite
was run at the end anyway: 1032 tests, OK (skipped 8).
